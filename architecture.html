Deepam CRM — how it actually runs

Four leaky sheets and a POS export, resolved to one customer per phone number. This is the request path, the import pipeline, the data model, and the two places the app is deployed — traced from src/proxy.ts, src/db/, the API routes, and the Docker/CI config, not summarized from the design docs.

Stack Next.js 16.2 · React 19.2 · Drizzle · Neon Postgres Auth Clerk, invite-only Commit e522f6f Audited 2026-08-08
01

System overview

One Next.js App Router codebase is deployed twice — Vercel (git-integrated, auto-deploy) and AWS App Runner (a Docker container built from the same repo) — and both copies talk to the same Neon Postgres database and the same Clerk instance. There's no queue, no worker, no cache tier: every request is handled inline by a Server Component or a Route Handler, and Postgres is the only stateful dependency besides Clerk's session store. The AWS path carries no AWS-specific application code — App Runner just runs the standalone server (output: 'standalone') in a container; it was added because Amplify's documented Next.js support tops out below v16, not because the app needed AWS.

02

Request flow & the auth boundary

Every route is closed by default. proxy.ts — Next 16's rename of middleware.ts — runs Clerk on every request except /sign-in and /api/health, but the project treats that as an optimistic check, not the real gate: with no Clerk keys configured, every route returns 500 rather than serving a page. The check that actually matters runs a layer deeper, inside the handler itself — requireUser() for pages, requireApiUser() for API routes — so a badly-edited matcher still can't leak data.

03

Data ingestion — two-phase preview/commit

Four source formats land as uploaded .xlsx/.csv files. Every one is parsed, normalized through a single phone module, and staged — never written to a canonical table on the strength of an unreviewed file. Commit is a single pooled transaction that upserts on natural keys (phone_e164, voucher_no, submission_id), so re-uploading the same sheet twice is a no-op rather than a duplicate.

04

Data model

customers is deliberately thin — a normalized phone number as the only identity key, everything else enrichable. Every source keeps its own table, so a fifth channel is a new table and a parser, not a migration on the busiest table in the system. customer_attribution is a materialized view rather than a column: first-touch channel and lifecycle both depend on rules (channel priority, attribution window) the team expects to keep tuning, and a view is refreshed where a column would need a backfill.

05

Deployment & operations

Vercel deploys automatically on every push. The AWS path is deliberately slower: GitHub Actions builds and pushes a Docker image to ECR via OIDC (no long-lived AWS keys stored in GitHub) on every push to main — and stops there. Going live on App Runner is a separate, manual aws apprunner start-deployment, the same preview-then-commit caution the app applies to its own imports. Migrations are never run by the container; they're a manual npm run db:migrate against the real database before first traffic.
